# ORG-01D4C original-owner action and budget authority

1 November 2026. Implemented, installed and database-validated in preview; hosted owner acceptance and production execution remain pending. [D4 requirements](org-01d4-actions-and-budgets.md), [D4B storage](org-01d4b-action-ownership-storage.md), [organization architecture](org-01-organization-architecture.md), [backlog](backlog.md).

## Delivered boundary

The [one-time migration](migrations/2026-11-01-organization-action-authority.sql) converts action lists/single reads/history/counts, creation, editing/completion/reopening and deletion to `owned_action_operation`. Quota status/consumption/warning bookkeeping use `owned_usage_operation`. Both accept only cookie-authenticated calls, bind the actor to `auth.uid()`, resolve the selected current original-owner workspace and return a closed `org-operations-1` response with actor/organization binding. There is no caller-supplied actor, tier, budget limit or overage grant. An optional single `organization_id` UUID selects the workspace on action and usage HTTP routes; malformed, duplicate or foreign selection never falls back to a default target.

Original owners remain the only enabled actors. No invitations, teams, practice/advisor relationships, ownership transfers, organization billing accounts, commercial limit changes or new AI execution are enabled. Existing action ranking/filtering/presentation, status/completion semantics and legacy history are preserved. ACTION-01's new sorting/sharing requirements remain separate. QuickBooks remains parked. D5 still owns the complete weekly graph conversion; D6 must finish cross-domain/lifecycle enforcement before collaboration.

Action creation/deletion no longer use raw table DML, and updates call the new authority before delegating to the existing validated atomic status/history engine as an owner-only implementation detail. List/history/count adapters validate scoped response envelopes and row owners. Direct SELECT RLS now checks verified original-owner organization scope for actions, history and usage. Trusted service SELECT is retained for the unconverted forecast-discard dependency; it is not a delegated-access grant.

## Locking, coverage and capacity

The capability-specific operational resolver uses READ COMMITTED and takes organization `FOR UPDATE` → current verified Auth/membership `FOR SHARE NOWAIT` → current profile `FOR UPDATE NOWAIT` → subscription `FOR NO KEY UPDATE NOWAIT` when needed → action/forecast/item/usage resources. It resolves the live original-owner graph and current revisions again after acquiring the root. This shares D3's reviewed lock mechanics without representing action/quota authority as a monthly financial capability. A verified explicit create may provision a missing default profile/organization atomically; explicit foreign selections never provision. Read operations do not create missing setup.

Legacy profile/Auth, subscription and draft/version-first paths can hold predecessor resources. NOWAIT returns 409 `WORKSPACE_BUSY` rather than holding a root while waiting in an inverted cycle. Forecast handoff locks and validates its version/header/item before inserting the action. Existing foreign-owner and D4B business/header checks remain. Reads use the same current owner graph; a missing/invalid migration or graph returns unavailable rather than silently accepting an unscoped result.

Creating or reopening an active action requires eligible current target coverage. Capacity is counted by stored organization under the subscription lock: Starter 10, Core 50, Growth/Advisory unlimited, suspended 0 new slots. The retained AFTER capacity trigger uses organization counts and bounded subscription locking; it does not acquire an earlier organization root from inside a legacy resource-first writer. Completion, deletion, completed-record creation and edits that acquire no new active slot retain their remedial behavior after lapse or downgrade, including when already above a lower limit. Exact action/usage API paths defer subscription decisions to the target authority after normal Auth/email verification; neighboring and unrelated routes retain their paid boundary.

New writes atomically record current actor, organization, resource reference, operation, policy/revisions, request correlation ID and database time in private immutable `operational_write_events`. Create/update/delete and finite admitted quota consumption are recorded; denied quota admission and untracked unlimited admission create no attribution events. No names, financial amounts, workbook/provider payload or historical author inference is stored there. Events have stable references and survive action/Auth removal with the organization tombstone. Existing status-history deletion behavior remains; new provenance does not depend on that deletable history. Request IDs are correlation metadata, not an exactly-once retry cache.

## Shared budget policy and usage display

SQL derives limits, allowed overage and the exact current billing period from the locked target subscription. Core retains 20 Ask CFO questions / 3 insight runs; Growth retains 150 Ask CFO questions with fair-use overage and unlimited insights; Advisory metrics remain unlimited/untracked. Denial leaves the count unchanged. Approved overage increments and reports throttling. Existing counters, historical `actions_created`, periods, warning timestamps and source identity are not reset or rebucketed. A user/period key attached to another historical organization fails closed instead of moving its budget into a recreated workspace.

Finite operations require a stored current billing window with valid start/end dates. Missing, expired or contradictory evidence returns unavailable; no request-time clock is invented as a fresh budget anchor. This can make manually tier-switched test accounts without real billing-period data show usage as unavailable. It does not grant a new allowance or require changing Stripe identity. Unlimited admission still checks current verified organization/coverage but creates no usage row and does not require a finite-period counter.

The usage status route returns real current active-action counts from `actions`, not a nonexistent `actions_active` usage record. It preserves the existing Starter/Advisory empty-card behavior and validates the Core/Growth metric set. The usage card checks HTTP/result validity, displays an explicit unavailable message on failure and allows Refresh; it no longer treats an error response as a successful empty usage list.

The dormant `usageGate` helper now calls cookie authority and uses SQL-returned tier/limit/period/organization; its old caller policy/date parameters are ignored. Warning bookkeeping is bound to the exact consumed period string (including fractional precision), current Growth scope and an existing count at/above the warning threshold. Delivery/mark failures remain ancillary to committed consumption. No new background service grant is provided. Historical `consumeUsage`/`getUsage` exports remain for old contract references; current routes/helper do not use their legacy policy-bearing path. The old SQL engine is owner-callable only. Future AI work must use the new authority and define real execution/replay/refund behavior separately.

Ask CFO and AI Insights still return `501 FEATURE_NOT_IMPLEMENTED` before quota work. No provider call, usage warning email or customer quota consumption is activated by this release. Stripe customers/subscriptions, prices, Founding identity, sales flags and billing webhook semantics are unchanged.

## Privilege closure and retention

All application roles lose raw INSERT/UPDATE/DELETE, TRUNCATE, REFERENCES and TRIGGER on actions/history/usage, including column-specific write/reference privileges. Legacy `update_action_with_audit`, `consume_usage`, retired `increment_usage` and `get_active_action_count` execution is revoked from application roles. The new wrappers and SELECT predicate are authenticated-only; service-role credentials alone cannot invoke them. Private ledger/helper grants remain closed. No service or separate-DML fallback occurs if authority is missing or fails.

D4B's immutable organization/profile scope, correction evidence and composite keys remain. Profile deletion can still detach legacy business links, and Auth removal retains the existing action/history cascade versus usage NO ACTION FK distinction. Private correction/operation evidence survives deletion. D6 still needs to reconcile wider retention and lifecycle policy; this release does not erase usage to make account deletion pass.

## Hosted owner acceptance

1. Open Actions and the Dashboard panel. Confirm existing actions, sorting, due/completed dates and history look unchanged.
2. Create a temporary action, complete it, reopen it and check history/counts; delete it if desired. If the account is near its limit, confirm a denied addition leaves no extra action/history.
3. Open Billing usage. With a valid billing window, Active actions must match the actual active list. A manually upgraded test account without a current window should show unavailable, not a fabricated zero allowance. Refresh must behave cleanly.
4. Open Cash planning and any forecast-linked action. Ask CFO/Insights remain coming-soon/unavailable and must not spend allowance. No manual financial import/Clear Data is needed specifically for D4C; D3 acceptance remains separate.
