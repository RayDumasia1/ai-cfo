## Scope and authority

The [one-time migration](migrations/2026-10-29-organization-monthly-write-authority.sql) closes monthly import review/no-op/confirmation, Clear Data, failed-import audit and their profile dependencies as one group. It preserves existing calculations, import modes, blank/zero meaning, revision capture/pruning, settings preservation, opaque data versions and billing identities. This remains an original-owner compatibility boundary. Teams, ownership transfer, practice/advisor access and organization billing are not enabled. Actions, usage and the weekly graph retain their existing boundaries until D4–D6; QuickBooks integration remains parked.

Cookie-authenticated clients call `owned_monthly_operation` for the closed operations `authorize`, `review`, `confirm`, `clear` and `audit_failure`. SQL binds the actor to `auth.uid()`; there is no caller-supplied actor parameter. An optional single UUID `organization_id` selects the target on HTTP write routes. Foreign, repeated or malformed selectors fail without falling back to the default workspace. An omitted selector resolves the current original-owner workspace anew on each request.

The locked resolver requires verified Auth, active customer/shadow organization, live legacy mapping, original owner membership, matching immutable D2 scope and current access/membership revisions. Financial operations additionally require that target's eligible legacy subscription; suspended or lapsed coverage grants no financial access. The exact import/review/confirm/data proxy paths defer paid checks to this authority after normal authentication/verification, rather than making an independent actor-subscription decision. Other proxy routes retain their existing gates.

`authorize` is an early read-only access check before upload parsing. An eligible account without a profile can pass default-target preflight without creating anything. Only explicit preparation/clear or verified metadata setup provisions a missing profile and B+D2 identity atomically. A foreign explicit selection never provisions a workspace. The final operation always repeats authorization under locks; preflight is not a reusable grant.

## Locking and review state

Existing-workspace writes use READ COMMITTED: organization row `FOR UPDATE`, current verified Auth `FOR SHARE NOWAIT`, membership `FOR SHARE NOWAIT`, profile `FOR UPDATE NOWAIT`, then subscription `FOR SHARE NOWAIT` for financial operations. After acquiring the root and dependent locks, SQL resolves the current graph and target entitlement again in a fresh statement. Stronger snapshot isolation is rejected. A newly provisioned, uncommitted workspace is the bounded bootstrap exception before a root exists.

Legacy Auth/profile deletion, subscription updates and weekly/provider writers can hold dependent rows first. D3 never waits on those rows while holding the organization root: contention returns PostgreSQL `55P03` and HTTP 409 `WORKSPACE_BUSY`, allowing a deliberate retry after the other operation finishes. This avoids introducing an organization/profile lock cycle while unconverted domains remain. Do not add a blocking root acquisition inside an old profile-first writer. D5/D6 must revisit the complete graph protocol before collaboration.

Review preparation returns a closed state fingerprint binding actor, organization, profile, current access/membership revisions, target tier, current Auth verification timestamp and the existing financial-state hash. Confirmation repeats those checks under the same locks and delegates to the unchanged reviewed engine within the transaction. The HTTP HMAC token is now version 2 and also binds organization, user, exact file digest/name, mode, closed state and expiry. It pins the resolved organization even if confirmation omits the selector. Outstanding older tokens require a fresh review. Review tokens authorize no other operation and are not persisted.

Settings edits preserve their prior import behavior: current settings are retained on import and ordinary settings-only changes do not invalidate financial review state. Auth verification or target tier changes do invalidate it. An identical v2 confirmation remains a semantic no-op: no financial/version/history/import-audit or new attribution event changes. Losing a committed HTTP response still requires refreshing; request IDs are correlation metadata, not an exactly-once replay cache.

## Privileges, profile callers and evidence

All eight legacy import/review/no-op/clear functions and aliases lose application-role execution, including `service_role`. The bodies remain owner-callable implementation details, invoked by the authenticated SECURITY DEFINER wrapper with an empty search path. Raw INSERT/UPDATE/DELETE on monthly rows, categories, import audit and revisions are revoked from all application roles. Monthly/category/import SELECT RLS now also checks persisted organization scope; C's monthly read RPC and adapter check that scope too. Revision browser reads remain denied. Trusted service SELECT remains for unconverted readers.

Profile UPDATE/DELETE and service INSERT are revoked. Verified authenticated INSERT remains available with own-user RLS for setup and INSERT RETURNING. `ensure_owned_business_profile` replaces profile UPSERT bootstrap; `update_owned_business_profile` allows only business name and the five existing financial thresholds, with validation and current owner locking. Verified owners can maintain this control metadata after subscription lapse without gaining financial access. `update_owned_profile_preferences` narrowly handles alert snooze choice and onboarding completion, keeping the first database completion timestamp. It cannot write financial identity or a data-version token. These dependent callers move in D3 because leaving their direct writes in place would either break existing flows or leave a broad bypass.

Service `UPDATE(id)` alone is retained on profiles to permit existing `SELECT FOR UPDATE` in weekly/provider functions. B's immutable identity guard rejects an actual identity change. Direct settings updates remain denied. A real legacy cash-plan draft call is exercised under the reduced permissions; this compatibility check does not convert weekly authority or resume QuickBooks work.

Private `organization_private.monthly_write_events` records current actor, organization/profile references, operation (import/clear/settings), policy/revisions, request ID and database time atomically with changed financial/settings operations. It stores no amounts, workbook or provider payload. Events are immutable and unavailable to anon/authenticated/service clients. Stable references survive Auth deletion alongside the organization tombstone; legacy financial/import/revision rows retain their existing deletion behavior. No authors are inferred for historical rows. Onboarding/snooze changes retain their narrow metadata semantics and do not fabricate financial attribution. Failed-import audit uses a controlled, sanitized original-owner operation; authorization/stale/contention failures do not create misleading import-error audits.
