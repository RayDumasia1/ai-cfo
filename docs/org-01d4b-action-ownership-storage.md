[D4 requirements](org-01d4-actions-and-budgets.md), [D conversion sequence](org-01d-financial-ownership-conversion.md), [parent architecture](org-01-organization-architecture.md), [backlog](backlog.md).

## Delivered storage contract

The [one-time migration](migrations/2026-10-31-organization-action-ownership.sql) adds non-null `organization_id` to `actions`, `action_audit_log` and `usage_tracking`. Organization/legacy-owner FKs reference D2's immutable private scope identity; actions additionally reference their organization/profile/owner tuple. Status history has an organization-qualified action/owner parent FK with the existing cascade behavior. Usage gains organization/metric/period uniqueness alongside the existing user/metric/period key, nonnegative count/limit checks and a valid-period check. Historical `actions_created` remains a distinct metric; no counters are renamed or interpreted as live active-action capacity.

The preview install repaired exactly **12** null action business links to their uniquely checked original-owner profile. It retained all original action details, statuses, due/completion dates, alert/forecast/item links and timestamps. All six original status-history rows were preserved. Preview had zero usage rows; the preceding rehearsal seeded three populated counters to verify count, period, limit, warning and timestamp preservation before rolling back the whole rehearsal.

Each repaired action has private immutable `organization_private.action_scope_repairs` evidence: stable action/organization/legacy-owner/profile references, null prior business reference, original row comparison fingerprint, fixed correction policy, database operator and real correction time. This is administrative correction provenance, not a newly inferred historical customer author. The MD5 row fingerprint is only an exact comparison aid, not an authorization signature. Evidence has no Auth/profile/action deletion FK and remains after their removal; its organization FK retains the organization tombstone. Application roles have no private schema/table/helper access.

No financial data, profile data version, Stripe identity, subscription, usage amount, tier limit, action ranking or sales flag is changed by installation. No API/UI code changes are required. Existing RLS policies, table grants and legacy action/update/capacity/usage engines remain in place. **D4C must still convert authorization, active-capacity and quota decisions before collaboration.** Original owners remain the only enabled actors. QuickBooks and unavailable AI endpoints remain parked/unavailable.

## Checked installation and preservation

The transaction takes SHARE locks on Auth, organization/membership/mapping/profile/scope, subscription and forecast dependencies, then ACCESS EXCLUSIVE locks on the three expanded targets. Five-second lock and 60-second statement timeouts bound installation; competing legacy lock orders may require retry after rollback during a quiet write window. Locks exclude target writes and lifecycle/mapping changes during validation/backfill. Replay, preexisting scope columns, missing D3/legacy engine prerequisites, unexpected deletion constraints, disabled RLS, and unknown/changed action or usage triggers abort the install.

The known `set_updated_at`, `actions_set_completed_at` and capacity trigger bodies are checked using whitespace-normalized source digests, enabled event definitions, security mode and return type. Both BEFORE UPDATE triggers are temporarily disabled during action backfill because they can change original updated/completion timestamps, even when only scope is being assigned. Capacity remains enabled and acquires no new slot for unchanged status/owner. Both suspended triggers are restored within the same transaction. Failure restores schema, data and trigger state through transaction rollback.

Every target row is captured before expansion and compared afterward. The only allowed changes are the three new scope columns and the preflight-proven null-to-profile action link. Missing or conflicting owner/profile scope, ambiguous detached/recreated workspace history, inconsistent audit parents, foreign forecast/header/business/item lineage, invalid counters/periods/metrics or duplicate keys abort the entire migration; no conflicting row is guessed, deleted or moved. Production rechecks its own live evidence under locks rather than trusting preview counts or the saved D4A report.

## Ongoing integrity and compatibility

SECURITY DEFINER triggers with empty search paths stamp the checked live D2/B scope on legacy action/usage INSERTs. A null action business input is stamped to that profile, so the old creation helper cannot keep generating unscoped actions. Explicit wrong organization/profile values are rejected. History inherits the matching action's organization and owner, rejecting foreign parents. Existing action forecast/item owner FKs remain; the new guard also checks the forecast header's business against the immutable action scope. D5 still needs the complete weekly graph's organization-qualified parent constraints.

Stored IDs, organization and legacy owner cannot be reassigned. Action business links can become null only when the referenced profile is actually deleted. History cannot be reparented, and usage metric/period-start keys cannot be changed in place. Trusted existing counter operations can still update counts, limits, end dates and warning state as before; D4C will close that alternate service path and derive current target policy inside authority. These integrity guards are not a substitute for that authorization cutover.

Profile deletion preserves organization scope while nulling legacy action business links. Auth deletion retains the existing distinction: actions/history cascade, while a populated usage row's NO ACTION Auth FK blocks deletion atomically. Tests remove only fixture usage explicitly to exercise the remaining cascade; no customer counter cleanup or retention change is installed. Correction evidence survives both action and Auth removal. D6 must resolve wider retention/lifecycle policy before collaboration.

## Validation evidence

The new 20 local SQL tests reconstruct the legacy base action/history/usage tables, then execute the actual historical monthly chain, B/C/D2/D3, action capacity/update, forecast storage/link/discard and atomic usage migrations before the real D4B SQL. They verify exact old-field preservation including unusual legacy completion timestamps, populated legacy counters and microsecond warning times, semantic capacity/complete/reopen behavior, late-audit atomic rollback, owner/service scope denial, composite FK rejection independently of stamping, private evidence, forecast handoff/discard protection, profile/Auth deletion, replay and failed-install rollback. Failed-install cases include foreign scope/history, invalid counts, partial scope columns, unexpected triggers/deletion policy, detached/recreated ownership and a late DDL collision after backfill.

The [preview driver](../scripts/validate-action-ownership-preview.mjs) supports `--rehearse` (populated counters + DDL + fixtures all rolled back), `--apply` (install once, then verify) and no arguments (verify an installed migration). It checks all public row-value fingerprints, the exact correction source fingerprints/references, composite scope, original RLS/grants, private privileges, real authenticated/service action/status operations, populated quota denial/overage/warning state, late-audit rollback, new-profile and Auth lifecycle, and actual legacy draft handoff. All validation fixtures roll back; identity sequences may consume values as with earlier verifiers. The only committed data corrections are the reviewed 12 preview business links plus their retained private evidence and new organization columns.

For an installed migration, independent sessions additionally prove legacy action admission is actually blocked by the subscription row lock using `pg_blocking_pids`, completes after release, and preserves row values after both transactions roll back. A second independent-session check proved profile deletion waits on an inserted action's profile reference, then legitimately detaches existing links after the action transaction rolls back. The deletion transaction also rolled back, and exact public row fingerprints matched. The verifier requires one dedicated account without retained forecasts for that rollback-only deletion check. This is compatibility evidence for the existing protocol, not D4C's future organization-authority or final shared-slot acceptance.

All **1,478 local tests** passed across 92 files; four remote probes were skipped.
